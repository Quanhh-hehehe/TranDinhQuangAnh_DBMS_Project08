## 1. Prerequisites
Before running this project on a new machine, ensure you have the following installed:
* **Python 3.10+**: Make sure Python and `pip` are added to your system's PATH.
* **MySQL Server 8.0+**: Running locally or via a remote host.
* **Git**: To clone the repository.

## 2. Installation & First-Time Setup

If you are cloning this project to a new machine, follow these precise steps to set up the environment:

### Step 1: Clone the repository
```bash
git clone [https://github.com/your-username/cinema-management-system.git](https://github.com/your-username/cinema-management-system.git)
cd cinema-management-system 
```
### Step 2: Set up a Virtual Environment

It is highly recommended to isolate the project dependencies.

```bash 
python -m venv venv

#On macOS/Linux:
source venv/bin/activate  

# On Windows: 
venv\Scripts\activate
```

### Step 3: Install Dependencies

Install all required Python libraries (`mysql-connector-python `, `pandas`, `bcrypt`, `Faker`, etc.).

```bash
pip install -r requirements.txt
```

### Step 4: Configure Environment Variables (`.env`)

CRITICAL: For security reasons, database credentials are not hardcoded. You must create a `.env` file in the root directory.

1. Copy the template: `cp .env.example .env` (or create a file named `.env`).

2. Fill in your local MySQL credentials:

```bash
DB_HOST=localhost
DB_USER=root
DB_PASSWORD=your_mysql_password
DB_NAME=CinemaManagementDB
DB_PORT=3306
```

### Step 5: Database Initialization & Data Population

1. Open your MySQL Workbench or CLI and execute the `database_setup.sql` file to create the schema, Views, Stored Procedures, and Triggers.

2. Run the data generation script to populate the database with synthetic records:

```bash

python Import_data_tables.py 
```

## 3. How to Run the Application

Once the setup is complete, start the application by running the main controller:

```bash
python main.py
```

Upon launching, you will be greeted with the Main Menu, allowing you to enter either the `Customer Portal` or the `Management/Staff Portal.`

## 4. User Guide: Customer Portal

The Customer Portal provides a seamless end-to-end booking experience.

* 1. Registration: Select `Register`. You will be prompted to enter your Name, Phone Number (must be valid format), and Password (which will be securely hashed via `bcrypt` before database insertion).

* 2. Login: Select `Login` and enter your credentials.

* 3. Explore & Filter Movies: Use the hierarchical menu to filter movies by Genre, Title, and Date. The system queries the `v_ScreeningDetails` view for real-time accuracy.

* 4. Book a Ticket:
    * Select a specific showtime.
    * The system will render a Dynamic 2D Seat Map (e.g., Rows A-J, Columns 1-15).
    * Available seats are mathematically generated by the system and rendered as `[ ]`, occupied seats as `[X]`.
    * Input your desired seat code (e.g., `C4`). The system uses `SELECT ... FOR UPDATE` (ACID transaction) to prevent race conditions. If successful, your ticket is securely booked.

* Manage Profile: Go to the Profile section to update your Phone Number or change your Password. Input validations will prevent malformed data.
* Cancel Ticket: Select an active booking to cancel it. (Note: Only possible if the screening hasn't started yet and respects the temporal constraints).

## 5. User Guide: Management Portal

The Management portal is protected by Role-Based Access Control (RBAC).

* Admin/Manager Login: Use the designated Admin credentials (e.g., `admin / admin123`).

Manager Features:

* Executive Reporting (Option 02): View real-time financial dashboards. The system uses the `pandas` library to transform raw SQL output from the `v_RevenueDetail` view into a professionally formatted CLI table, displaying Total Tickets Sold, Gross Revenue, and Occupancy Rates.
* Add a New Movie: Input Title, Genre, Duration, and Base Price. The system enforces strict numeric validations and uses parameterized queries to prevent SQL Injection.
* Update/Delete Movie: Crucial Business Rule: You can only delete untouched movies. If a movie has active tickets sold, the Python controller aggressively blocks the deletion to prevent `ON DELETE CASCADE` from destroying financial audit trails.
* Add Cinema Room: Input a Room Name, Total Rows, and Total Columns. The Python controller executes an automated nested loop algorithm to generate alphanumeric seat codes (A1, A2...) and initiates a bulk `INSERT` into the database.
* Schedule Screenings: Select a Movie, Room, and Time. The system performs multi-layered Spatial-Temporal validation. If the proposed time block overlaps with an existing screening in the same room, the system halts the operation and alerts the Manager of the collision.

## 6. Project Structure & Critical Files

Understanding the repository layout:
```text
cinema-management-system/
│
├── main.py                 # The entry point of the application
├── controllers/            # Python logic (routing, validations)
├── models/                 # Database interaction (SQL queries, Model classes)
├── views/                  # CLI UI rendering (menus, seat map displays)
│
├── database/               
│   ├── database_setup.sql  # DDL script (Tables, Procedures, Triggers, Views)
│   └── backup/             # Directory for database .sql snapshots
│
├── scripts/
│   └── generate_faker_data.py # Script to generate synthetic data records
│
├── logs/
│   └── system_activity.log # Persistent audit trail (Errors, DB rollbacks)
│
├── .env                    # Local Environment variables (DO NOT COMMIT)
├── .gitignore              # Ignores venv, __pycache__, .env, and logs
├── requirements.txt        # Python library dependencies
└── README.md               # Project documentation
```

About `.gitignore`
This repository uses `.gitignore` to maintain strict security and repository hygiene. Your local `.env` (containing passwords) and `venv/` (containing heavy libraries) will never be pushed to public version control, neutralizing the risk of credential leakage.


## 7. System Maintenance (Backup & Logs)

* Disaster Recovery (Backups): Relying solely on the active database presents a critical point of failure. Periodically run logical backups (via `mysqldump` or automated scripts) to export the schema and data into the `database/backup/` folder. This ensures historical financial records can be fully recovered with minimal downtime.
* System Auditing (Logs): All critical administrative actions and trapped errors (e.g., database deadlocks, failed transactions due to race conditions) are recorded in `logs/system_activity.log.` Administrators can use this immutable audit trail for post-mortem analysis and security auditing.
